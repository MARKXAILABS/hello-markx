boundary this phase exposes: real path routing, a reserved `phone` prefix, an injected static root
served off an exact-filename allowlist, the phone's own rate bucket and auth lockout, the single-use

door — *"a strong generated token, never a user-chosen password"* and *"rate limiting and lockout on
the auth endpoint"*. DAEMON-05's own closure is claimed by plan 02-10; this plan satisfies those two
bullets and hands them forward.

**Why the whole server contract ships in one wave rather than being split with plan 02-09.**

verifier all rewrite `handleRequest`/`verifySecret` in one file that has exactly one copy — *"one
owner for `webhook.ts`, both requirements in the same plan or in strictly sequential plans, never
parallel."* Splitting the data endpoints out to plan 02-09 would mean 02-09 reopening `webhook.ts`
to fix a shape mismatch discovered from the client side. So the server is complete and
curl-verifiable here, against a fixture directory; plan 02-09 adds `resources/phone/**`, the
`extraResources` entry and the client that consumes it.

Output: a door that answers correctly to seven request classes before a single phone asset exists,
and a SUMMARY that says out loud which of its properties were never tested against a real device.
