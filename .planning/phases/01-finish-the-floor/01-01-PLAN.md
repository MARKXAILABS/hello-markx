## Recovery — what to do when the Electron bump breaks the native rebuild

Not a "fallback version". There is no independently-revertable piece: `better-sqlite3` 11.10.0 is
raw-V8 and cannot compile against Electron 43's V8 15, and 13.x declares `engines.node >= 22`, so
"Electron 43 with the old sqlite" and "Electron 32 with the new sqlite" are both non-states. The
unit of revert is Task 2's whole commit.

**How you know it broke** — in the order the signals fire:
1. `npx electron-rebuild -f` (postinstall) exits non-zero. That is the rebuild itself failing.
2. `tools/patch-node-pty-conpty.cjs` exits 1. Per D-05 this means **node-pty's sources changed**,
   not that Electron changed. `node-pty` is exact-pinned at `1.1.0`, so if this fires while
   `grep '"node-pty"' package.json` still reads `1.1.0`, a wrong tree got installed — wipe
   `node_modules` and `npm ci` again before concluding anything about Electron.
3. Everything exits 0 but the module will not load under the Electron ABI. Both natives are N-API
   (`better-sqlite3` → `node-addon-api ^8`, `node-pty` → `node-addon-api ^7`), so a plain-Node
   `require()` proves nothing about Electron. The load check that counts is Task 3's `npm run e2e`
   and, for the ConPTY path, Task 4's live Windows run — a failed native load degrades silently to
   defaults rather than throwing, which is exactly why D-09 exists.

**The recovery sequence**, run in this order:
1. `git rev-parse HEAD` — record the broken SHA in the SUMMARY before touching anything.
2. `git revert --no-edit <Task 2 SHA>`. This returns `package.json`, `package-lock.json` and
   `electron-builder.yml` together. Do not cherry-pick parts of it.
3. `rm -rf node_modules && npm ci`. **Mandatory** — reverting the lockfile without wiping
   `node_modules` leaves Electron-43-ABI `.node` files sitting under an Electron 32 install, which
   is the works-locally/red-on-CI split this plan already wipes `node_modules` to avoid.
4. Do NOT revert Task 1's loader commit. It is deliberately a separate commit and was proven green
   on Electron 32 before the bump landed; reverting it re-opens D-25 and re-breaks four later
   requirements for no reason.
5. Task 3's e2e assertion (`electron` major >= 43) will now be RED, correctly. Do not relax it to
   make the tree green — that is the one automated guard against a silent revert to 32.

**The state this leaves the repo in, stated plainly:** a buildable dev tree on Electron 32, with
FLOOR-03 still open, Task 3's gate red, and the whole phase still blocked — because every other
plan in this phase is gated on this one (D-03). A revert is a stop, not a recovery. Report it as a
blocked phase and re-plan (retarget the bump, or fix the specific native break) rather than
proceeding to Wave 2 on Electron 32.
