<objective>
Close the four defects in `sweepTaskReviews` — three more than the roadmap names — so that "done"
actually means someone else checked, and pin VERDICT-03's already-satisfied behaviour with a named
test rather than rebuilding it.

Purpose: FLOOR-08 as written is satisfiable by code that reviews nothing. Three separate mechanisms
lose reviews silently:

1. **Consumed transition edge.** `sweepTaskReviews` records the card as `done` BEFORE the loop runs
   (`hive.ts:1766`), so `if (!reviewer) continue` (`:1774`) permanently consumes the transition — a
   card finishing while every other agent is busy is never reviewed again.
2. **Missed transition.** `!previous.has(task.id)` (`hive.ts:1772`) skips any card that was not in the
   PREVIOUS snapshot. The sweep is throttled to `SWEEP_INTERVAL_MS = 60_000` (`hive.ts:238`, `:1813`),
   so a card that is created AND flipped to `done` inside one 60 s window is *never seen in a
   non-done state by any snapshot* and is dropped forever — a whole class of fast cards that no
   retry can recover, because no obligation is ever minted for them. This is the defect that makes
   the phase's own criterion 5 satisfiable by code that still loses reviews.
3. **Refusal is terminal.** `task.review` staying truthy after a refusal means the refused-then-fixed
   path, where a second look matters most, is unreviewable.

**What the snapshot is for, stated once so task 2 and this objective cannot drift apart (red-team
round 2).** The mint rule this plan prescribes IS a snapshot test —
`if (previous.get(task.id) !== 'done') this.owesReview.add(task.id);` — and that is deliberate. Two
separate jobs are being done by two separate guards, and confusing them is how the storm gets shipped:

- `if (!previous) return 0;` (`hive.ts:1767`) suppresses the **first** sweep after a cold start, and
  ONLY the first. It does nothing on sweep 2 onward.
- `previous.get(task.id) !== 'done'` is what keeps every sweep from the second onward quiet against a
  ledger full of historic `done` cards: on sweep 2 the boot seed already recorded them as `done`, so
  the rule mints nothing for them. **This is the anti-storm invariant**, and the doc comment at
  `hive.ts:1730-1735` — *"a ledger full of historic 'done' cards is never mass-reviewed at boot"* — is
  a promise this plan must leave TRUE.

Defect 2 is closed by that same rule without any extra branch, because `previous.get(missingId)` is
`undefined`, which is `!== 'done'`. Deleting `!previous.has(task.id)` is therefore the whole of the
fix — no second minting path is needed, and none may be added. **In particular there is no startup
rebuild of `owesReview` from the persisted board.** An earlier revision of this plan ordered one; it
re-opens the exact storm the comment forbids (sweep 1 returns 0 via the seed guard, sweep 2 mints
nothing new, but a rebuilt set already holds every historic card, so `owesReview.has(...)` passes and
one `query` is mailed per historic card). The obligation set is process-local by design: an obligation
minted in a session that ends before a reviewer was free is lost, which is the same accepted trade the
`hive.ts:1730-1735` comment already states for a card finished while the app was closed.

**Named residual — the sweep is a poll.** Because the mint is a transition test between two snapshots
60 s apart, a card that is `done` at sweep N, is reopened by a writer that does not go through
`applyReviewVerdict` (a god hand-editing `tasks.json`), and is back to `done` before sweep N+1 has
identical durable state at both snapshots and mints nothing. No snapshot-based rule can see a change
that is undone before the next observation. This plan does not claim to close it: it names it
(T-P03-07), and task 2 corrects the source comment at `hive.ts:1755-1760` that currently overclaims
*"catches every writer including a god that hand-edits tasks.json"*. That comment is a false claim in
source, which is precisely what this phase exists to remove.

Output: an obligation `Set` (not a second state machine, not a second status field), a mint rule that
no longer requires the card to have existed in the previous snapshot, a refuse→re-add, a per-sweep
prune against the live board, two corrected source comments, and five tests.
</objective>

exactly the card that deserves a review, not the historic backlog. Deleting `!previous.has(task.id)`
therefore does not re-open the mass-review-at-boot problem, **provided the `!== 'done'` half survives
and nothing else mints.** `test/hive-protocol-v2.test.cjs:220` proves only the FIRST-sweep half (it is
green purely because of `if (!previous) return 0`), and `:233` proves only that a card with an OPEN
review is not re-queried — a storm card has no review, so neither existing test would catch a
sweep-2 backlog storm. Task 3's test 5 is the assertion that covers the second sweep, and it is the
