<objective>
RECORD-05's restore points, and RECORD-02's one remaining call site.

**Purpose — RECORD-05.** The requirement forbids disturbing the operator's **index, working tree,
branches, `git status` and `git log`**. D-20 scored four candidates against exactly that list and only one
passed all five: a **separate `GIT_DIR` over the operator's work-tree**. `04-RESEARCH.md` § Pattern 6 then
**ran it end to end on this machine** (`git version 2.52.0.windows.1`, Windows 11) and measured:
`rev-parse HEAD` identical, `status --porcelain` identical, branches identical, reflog line count
identical, nothing added under the operator's `.git/`, the operator's own `.gitignore` honoured for free
(a gitignored `build/` produced **0** entries), per-file restore leaving neighbours untouched, and two
snapshots of four files deduping to **10 objects / 80 KiB**.

Three further measurements the CONTEXT does not name, all of which change the implementation:
- **`GIT_INDEX_FILE` is not required.** `--git-dir=<store>` alone makes the index default to
  `<store>/index`. D-20's `GIT_INDEX_FILE` is belt-and-braces, not a requirement — and requiring it would
  force `git.ts:6-28`'s `runGit` to grow an `env` parameter it does not have (Pitfall 7).
- **One `git init` in a subdirectory kills the entire restore point** (L-06). An uncommitted embedded repo
  makes `add -A` print `error: 'nested_empty/' does not have a commit checked out` and **exit 128**,
  adding nothing; an embedded repo *with* commits is worse and quieter — it records a **gitlink, mode
  `160000`**, so the snapshot claims a subtree it does not contain. **Agents create worktrees inside the
  operator's repo** (`git.ts:518 listWorktrees`). Mitigation, measured working: discover nested `.git`
  entries and write them into `<store>/info/exclude`, which lives in the shadow store and touches nothing
  of the operator's. After that, `add -A` exited **0**.
- **`restore.git/index.lock` contention is fatal, not retried** (L-07). Two concurrent `add -A` →
  `fatal: Unable to create '…/index.lock': File exists.`

**Purpose — RECORD-02's mirror.** Plan 04-02 built the `events` table and `appendEvent`/`eventsBetween`/
`pruneEvents`. The call site is `hive.appendLog` (`hive.ts:2485-2509`), which this plan owns in wave 2.
Per RESEARCH § Pattern 5 the recommendation is **mirror, do not move**: keep the `appendFileSync` and the
8 MiB rotate exactly as they are (crash-safe, and what `logTail` reads) and add a best-effort
`persist.appendEvent(...)` beside it — additive and reversible, so a wrong schema guess has not also
destroyed the event log.

**Output.** `restorePoints.ts`, its wiring, the `appendLog` mirror, and one test file with three cases.
</objective>

<planner_decisions>
Two things `04-CONTEXT.md` left to the planner, decided here so no executor has to guess.

**1. One store per operator repo, keyed by a hash of the repo path** — settling RESEARCH § Open Question 4.
`RegistryAgent.cwd` is per agent (`hooks.ts:947-956`) and `hooks.ts:809-812` describes cwd as "the user's
project", so one floor can plausibly have agents in several project repos. A single floor-wide store would
then snapshot whichever repo happened to be first and silently ignore the rest. Store path:
`<harnessHome>/hive/restore/<sha256(realpath(repoRoot)).slice(0,16)>.git`, with the full real path written
into `<store>/description` so a human can tell which store is which. A per-repo store costs nothing extra
and is the safe shape. **Hash `realpathSync.native(repoRoot)`, never `realpathSync`** — see planner decision 5.

**2. The directory name is `restore`, NOT `backups`** — D-21's named collision. `backups` is already taken:
`reflect.ts:263` uses `hive/backups/<stamp>/` for memory-condensation generations, with its own
`pruneBackups` retention (`reflect.ts:552`, `KEEP_BACKUPS` at `:47`). Restore points placed there would be
pruned by a mechanism that was never meant to see them.

**3. Cadence and pruning.** Snapshot on a timer registered in `floor/boot.ts` beside `fleetTimer`
(`boot.ts:155`), default **every 15 minutes**, with a trailing debounce so a burst of activity does not
queue snapshots. Prune by `update-ref` to an older commit plus `git gc` on the bare store, keeping
**48 hours** of snapshots — enough to satisfy "put one file back to how it was at 02:00" with margin, and
bounded. Both numbers are `[ASSUMED]`, both are plain constants, both are cheap to change. **ADR-0003's
bias applies to the prune**: when we cannot prove a snapshot is safe to discard, keep it — a prune that
errors must leave the store intact rather than half-collected.

**4. The `events` retention bound is `[ASSUMED]` 30 days, and it is decided HERE, not inherited.**
Plan 04-02 shipped `pruneEvents(olderThanMs)` with a 30-day default; this plan is the first thing that
CALLS it, so the number becomes a live policy here and carries the marking here. RESEARCH marks it A3 —
nothing in the research session measured how far back an operator actually asks "what did the floor run".
30 days is a starting value, stated as one, and it is one `DELETE FROM events WHERE ts < ?` away from
being changed. Do not re-derive it in the SUMMARY as if it were measured.

**5. The store key uses `realpathSync.native`, not `realpath`.** On win32 `fs.realpathSync` does NOT
canonicalize drive-letter or path-segment case, and `fs.realpathSync.native` does. Without `.native`,
`E:\repo` and `e:\repo` hash to two different stores and the operator's restore points silently split in
half — with each store holding a partial history and neither knowing about the other. This is the same
class of defect as the cadence and retention numbers above and it gets the same treatment: decided in
writing, and asserted by a test.
</planner_decisions>
