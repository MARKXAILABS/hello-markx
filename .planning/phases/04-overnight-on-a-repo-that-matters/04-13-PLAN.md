<objective>
GATE-04: one engine runs with its own sandbox **on** and still completes hive housekeeping — it finishes a
task, mails, and writes memory with no write refused.

**Purpose.** D-14 measured the blocker and it is not a security judgement, it is two directories.
`src/shared/agentProvider.ts:262-272` ships codex with
`autoModeFlag: '--dangerously-bypass-approvals-and-sandbox'`, and the comment above it at `:262-270`
states the whole reason: *"The earlier `-a never -s workspace-write` confined writes to the PTY cwd (the
user's project), but a hive worker must also write to its agent folder at `hive/agents/<id>/` … a
DIFFERENT path tree from cwd, which workspace-write blocked, so codex workers couldn't do HIVE PROTOCOL
housekeeping."* The fix is **writable roots**, not dropping the sandbox. `codex --help` on this machine
documents **`--add-dir <DIR>` — "Additional directories that should be writable alongside the primary
workspace"** — a flag-level path to the same outcome that does not go through `config.toml` at all.

**D-15 is binding and is not negotiable down.** Per-engine, opt-in, with a verified fallback. Eleven
engines, three OSes, different sandbox semantics; the failure mode of a floor-wide flip is *"the floor
silently stops working at 3am"*, which is worse than the failure it prevents. **Deliver exactly one
engine.** Criterion 2 asks for "at least one". Shipping one engine that provably finishes a task, mails,
and writes memory with no write refused satisfies it; shipping five half-verified ones does not.

**L-08 is the landmine, and it is the reason two files must have one owner in one wave.** The auto-mode
flag is appended **twice, independently**: in main at `src/main/config.ts:1067-1068`
(`commandForAutoMode`, declared `:1058`) and in the renderer at
`src/renderer/src/store/config.ts:430` (`buildSpawnCommand`, declared `:405`). They sit in **different
tsconfig projects** (`tsconfig.node.json` / `tsconfig.web.json`), so `npm run typecheck` **will not** catch
a drift. A sandbox opt-in that edits only one produces a command the operator reads at
`AddAgentModal.tsx:971` that is not the command that spawns — the precise shape of the failure GATE-04's
own warning names.

**The claim depends on plan 04-01's spike AND on this plan's own live run, and the two settle different
things.** `04-SPIKE-codex-sandbox.md` carries a single `VERDICT:` line — but it was produced with
`codex exec`, and `hiveProvisioning.ts:207` records in this repo's own words that *"hooks fire in
INTERACTIVE codex sessions (how hive workers run), not in headless `codex exec`."* Upstream
[openai/codex#23552](https://github.com/openai/codex/issues/23552) is a **prompt** defect, and a
non-interactive run cannot prompt — so it cannot reproduce the defect even when the defect is present.

Therefore: **a `WORKS` verdict licenses this plan to BUILD, not to CLAIM.** The claim is decided by task 4,
which spawns a real interactive agent through the floor — the same path a hive worker takes. A
`REFUSED/PROMPTED` verdict is stronger evidence in the other direction (if it prompts even non-interactively
it will certainly prompt interactively), and in that case GATE-04 ships built-and-`LIVE-UNVERIFIED` citing
the issue, with the marker in the ledger in the same commit. Every outcome is a first-class result and every
one of them is decided by a run. **Guessing is not.**

**Output.** The preset variant, both splices, the Settings row, the marker (if needed), and a live run.
</objective>
