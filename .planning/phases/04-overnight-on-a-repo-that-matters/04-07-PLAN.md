<objective>
VIGIL-03's second half: **one list, two readers**, and the mechanical proof that the reader in main needs
no renderer.

**What plan 04-03 already shipped, and why this plan is smaller than it was.** The first draft of this
plan owned `pty.ts` and built a second detection mechanism there — a tap on `proc.onData` or a poll timer,
with its own state and its own invalidation. The revision moved detection into plan 04-03's composition-root
wiring, where it is one derived read of `PtyManager.outputTail(ptyId)` (`pty.ts:930-933`) — a ring
`pty.ts:64-71` documents as *"recorded whether or not a renderer is listening"*. No new PTY state, no
cache, no latch, and the recovery path falls out for free. So `src/main/pty.ts` is **not in this plan's
scope at all**, and with it goes the whole `:745-800` boundary problem that plan 04-05 rewrote in wave 1.

**What is left is the part that still matters, and D-29 gives all three reasons:**

1. **Off-screen coverage.** `src/renderer/src/components/terminalPool.ts:59` has a single `onData` slot
   *"set by whichever view is mounted"*, so renderer detection is mount-scoped by construction. An
   off-screen agent is never marked blocked, so `stopArmDecision`'s guard (`useHive.ts:169`) never fires
   for it — which is D-28's point.
2. **Headless correctness.** Phase 2 delivered a floor that runs with no window
   (`src/main/floor/headless.ts`). A renderer-resident parser **does not exist at all** on a headless
   floor, so *every* agent is undetectable there, not merely the unmounted ones.
3. **One list.** Two copies of a regex list drift, and the copy that drifts is the one nobody is looking
   at. `usePtyParser.ts:31-37` must stop being a declaration and start being an import.

**Output.** The renderer's local list deleted, the per-engine limit written into the shared module, and a
test that proves detection in a process with no renderer module loaded.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| PTY bytes → main's tail ring → agent status | An LLM-controlled process's stdout is parsed by main and its matched line is later rendered. This is the untrusted-display-data boundary 04-UI-SPEC rule A8 governs, and plan 04-03's `matchBlockHint` is where it is bounded. |
| main-owned status → renderer + headless floor | The renderer renders a state main owns; the headless floor has no renderer at all and must behave identically. |
| one list → two tiers | A second copy of the list is a second security-relevant behaviour that nobody is looking at. This plan's whole job is that there is only one. |
