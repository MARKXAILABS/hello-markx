<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Electron main <-> local filesystem | `harnessHome`-derived paths for `harness.db` and `KG_ROOT` are operator-configured local directory paths |
| Onboarding IPC (`config:update`) <-> main | Renderer-supplied config patch, already validated/normalized by `writeConfig` before this plan's hook fires |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|------------------|
| T-03-01a | Information Disclosure | `db.ts` default-path change | accept | The DB still lives under an operator-chosen `harnessHome`, a path the operator already fully controls and already trusts with the hive's memory/task data; no new secret or credential is newly exposed by relocating the DB file itself |
| T-03-01b | Tampering | `repoint()` mid-session | mitigate | `repoint()` only fires inside the single, already-guarded `!hiveWasEnabled && hive.enabled()` transition — it is never reachable from an ordinary `config:update` patch, so a malicious/buggy renderer patch cannot trigger a repeated close/reopen storm |
| T-03-01c | Denial of Service | existing-install data left at the old path | accept | Declared in CHANGELOG.md per Task 3; the data is not deleted, only unused post-upgrade — recoverable by hand if ever needed, and explicitly not silent |
</threat_model>
