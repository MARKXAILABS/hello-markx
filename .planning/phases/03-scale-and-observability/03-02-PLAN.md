From `src/main/hive.ts`'s cost-ledger accumulator (current, verified this session — the pure
function Task 2 modifies; note the NUL separator, not a space):
```
private costCumulative = new Map<string, { tokens: number; usd: number }>();
private applyCostRow(
  byTask: Map<string, { tokens: number; usd: number }>,
  cumulative: Map<string, { tokens: number; usd: number }>,
  row: { agent_id?: string | null; session_id?: string | null; task_id?: string | null; input?: number; output?: number; usd?: number }
): void {
  const key = `${row.agent_id ?? ''}\u0000${row.session_id ?? ''}`;
  const now = { tokens: (row.input ?? 0) + (row.output ?? 0), usd: row.usd ?? 0 };
  const previous = cumulative.get(key);
  const delta = previous
    ? { tokens: Math.max(0, now.tokens - previous.tokens), usd: Math.max(0, now.usd - previous.usd) }
    : now;   // <- a brand-new key's WHOLE value becomes its own delta — correct for a live OTel
             //    session (which genuinely starts at zero), WRONG for a fallback series (whose
             //    first observation carries an ALL-TIME cumulative total, per transcriptFallback above)
  cumulative.set(key, now);
  const taskId = row.task_id;
  if (!taskId) return;
  const acc = byTask.get(taskId) ?? { tokens: 0, usd: 0 };
  acc.tokens += delta.tokens; acc.usd += delta.usd;
  byTask.set(taskId, acc);
}
```
`row.session_id === ''` is ALREADY the exact, existing marker for "this row came from
`transcriptFallback`" — `readAgentUsage`/`readCodexUsage`-sourced rows are the ONLY producer of an
empty (as opposed to absent) `session_id`, so this plan's fallback-specific branches key off that
value rather than inventing a new discriminator field. `src/main/usage.ts:201-203` documents the
OTHER half of the hazard this plan closes: `readCodexUsage`'s 256KB tail window can transiently
under-report a total for one read (a record larger than the window falls out, "reappears on the next
turn's record" per that file's own comment) — under a diff ledger, an unconditional `cumulative.set`
would let that transient dip get overwritten as the new baseline, so the record's later reappearance
re-credits the same tokens a second time.
